
# EventFlow — Decisions Registry

> Реестр согласованных продуктовых и архитектурных решений.
> Последнее обновление: 11 ноября 2026 года.

## 1. Назначение

Этот раздел фиксирует решения, принятые в процессе проектирования EventFlow.

Он нужен для того, чтобы:
- сохранять согласованную логику продукта;
- не возвращаться без причины к уже решённым вопросам;
- предотвращать противоречия между разными этапами разработки;
- передавать контекст между ИИ-платформами и участниками проекта.

## 2. Статусы решений

При работе с решениями необходимо различать:

- **Согласовано** — решение принято и должно учитываться при дальнейшей работе.
- **Предварительно согласовано** — направление определено, но детали ещё требуют уточнения.
- **Открытый вопрос** — решение пока не принято.
- **Изменено** — ранее принятое решение заменено новым.

Нельзя выдавать гипотезу или предложение за согласованное решение.

## 3. Организационная модель

<badge>Согласовано</badge>

- Используется сущность `organizations`.
- Связь пользователей с организациями реализуется через `organization_members`.
- Мероприятия связаны с организациями через `events.organization_id`.
- Пользователь может состоять в нескольких организациях.
- Пользователь может создавать несколько организаций.
- Создатель организации становится владельцем.
- Допускается несколько равноправных владельцев.
- На первом этапе предусмотрена только роль владельца.
- Владелец имеет доступ только к собственным организациям.

## 4. Управление организациями

<badge>Согласовано</badge>

- Удаление владельца из организации требует специальной административной процедуры.
- Пользователь может покинуть организацию, если в ней остаётся хотя бы один владелец.
- Последний владелец должен назначить преемника.
- Для организаций предусмотрены статусы: active, restricted, blocked, archived.
- Изменение статуса само по себе не удаляет данные и не отменяет права доступа.
- Вместо обычного удаления организации используется архивирование.
- Архивирование инициируется владельцем и проходит административную проверку.
- Ключевые операции должны фиксироваться в журнале аудита.

<badge color="warning">Открытый вопрос</badge>

Отдельная процедура удаления владельца из приватной клиентской организации требует уточнения.

## 5. Авторизация

<badge>Согласовано</badge>

- Основной способ входа — номер телефона и SMS OTP.
- Номер телефона хранится в формате E.164.
- Планируется использование Supabase Auth и SMS Hook/adapter.
- Пользовательская сессия сохраняется.
- Повторный OTP при каждом входе не требуется.
- Предусматриваются ограничения частоты запросов.
- Демонстрационный код `1234` должен быть изолирован от реальных аккаунтов.
- Смена номера телефона выполняется через отдельную безопасную процедуру.

<badge color="warning">Открытый вопрос</badge>

SMS-провайдер должен быть выбран до приёма первой предоплаты.

## 6. Коммерческая модель

<badge>Согласовано</badge>

- Регистрация бесплатная.
- Создание организации бесплатное.
- Демонстрационный режим бесплатный.
- Черновики мероприятий можно создавать без оплаты.
- Реальное мероприятие требует оплаченного права использования — entitlement.
- Entitlement расходуется при первой публикации или активации мероприятия.
- Создание черновика не расходует entitlement.
- До публикации entitlement можно перенести на другой собственный черновик.
- После публикации перенос не допускается.
- Удаление неопубликованного черновика восстанавливает entitlement.
- Временное скрытие опубликованного мероприятия не восстанавливает entitlement.
- По умолчанию entitlement бессрочный.
- Возврат оплаты отменяет соответствующее entitlement.
- Клиент может оплатить пакет до регистрации.
- Пакет выбирается до оплаты, стоимость должна быть известна заранее.

## 7. Уровни продукта и модули

<badge>Согласовано</badge>

Предусмотрены три типа функциональности:

1. Базовые функции.
2. Платные дополнительные модули.
3. Индивидуальные решения.

Уровень продукта определяется дизайном и объёмом решения, а не количеством подключённых модулей.

На первом этапе подключение специализированных модулей выполняет специалист.

Каталог модулей не обязательно должен быть доступен клиенту в виде самостоятельного магазина.

Индивидуальные решения могут становиться библиотечными модулями после стандартизации.

Материалы клиента не становятся библиотечным содержимым автоматически.

<badge color="warning">Не утверждено</badge>

Названия пакетов Essential, Premium и Exclusive не утверждены.

## 8. Медиагалерея

<badge>Согласовано</badge>

- После мероприятия гости переходят на общую страницу материалов.
- По умолчанию пользовательский контент скрыт до одобрения организатором.
- Предусматривается возможность автоматической публикации с предупреждением о рисках.
- Профессиональные фото- и видеоматериалы загружает клиент.
- Для крупных мероприятий может использоваться временная роль media_contributor.
- Эта роль не должна предоставлять доступ к гостям, RSVP и финансовой информации.
- Материалы не становятся собственностью EventFlow автоматически.
- Использование материалов в портфолио, рекламе и шаблонах требует отдельного основания или согласия.

<badge color="warning">Предварительно согласовано</badge>

Предварительные сроки:
- публичный доступ к галерее — 30 дней;
- загрузка материалов — день мероприятия и следующие 7 дней;
- архивная ссылка — 24 часа.

Эти сроки требуют окончательного подтверждения.

## 9. Принципы изменения решений

Если возникает необходимость изменить согласованное решение:

1. Указать исходное решение.
2. Объяснить причину пересмотра.
3. Описать последствия изменения.
4. Предложить новую формулировку.
5. Получить согласование.
6. Обновить документацию и историю изменений.

Не менять архитектурные и коммерческие принципы молча.
