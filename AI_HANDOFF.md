
# EventFlow — AI Handoff Instructions

## 1. Назначение документа

Этот документ устанавливает правила подключения любой ИИ-платформы к проекту EventFlow.

Главная задача — обеспечить непрерывность разработки при переходе между разными ИИ, разработчиками и рабочими средами.

ИИ должен использовать накопленную документацию, а не начинать изучение проекта с нуля.

## 2. С чего начинать работу

Перед выполнением любой задачи обязательно:

1. Изучить `AI_CONTEXT.md`.
2. Изучить `PROJECT_STATUS.md`, если он опубликован.
3. Изучить соответствующие разделы основной документации.
4. Проверить существующие аудиты по теме задачи.
5. Проверить принятые архитектурные и продуктовые решения.
6. Установить, какие вопросы уже решены, а какие остаются открытыми.

Если необходимые документы недоступны, сообщить об этом пользователю.

Не утверждать, что документ изучен, если он фактически не был открыт.

## 3. Запрет на бессмысленное повторение аудитов

Не проводить повторный аудит только потому, что к проекту подключилась новая ИИ-платформа.

Перед аудитом необходимо выяснить:

- проводилась ли такая проверка ранее;
- какие компоненты проверялись;
- какие результаты были получены;
- изменялись ли проверенные компоненты после аудита;
- появились ли новые требования или риски;
- достаточно ли актуальных данных для использования предыдущего результата.

Повторный аудит допустим, если:
- изменился соответствующий код или структура базы;
- появились новые функции или зависимости;
- изменились требования безопасности;
- обнаружена проблема;
- предыдущий аудит не охватывал нужную область;
- актуальность предыдущего результата невозможно подтвердить.

В таком случае ИИ должен объяснить причину повторной проверки.

## 4. Работа с историческими материалами

Исторические SQL-файлы и документы аудитов являются частью истории проекта.

Запрещено:
- автоматически переписывать исторические SQL-файлы;
- считать первоначальную схему актуальной схемой базы;
- запускать исторические SQL-файлы поверх действующей базы без проверки;
- выдавать старые результаты аудита за актуальное состояние;
- удалять исторические материалы без согласования.

Новые изменения базы оформлять отдельными миграциями.

## 5. Работа с архитектурой и решениями

До изменения архитектуры необходимо изучить:

- `02_architecture/`;
- `05_decisions/`;
- соответствующие разделы `AI_CONTEXT.md`.

Если новая задача противоречит ранее согласованному решению:

1. Указать противоречие.
2. Объяснить последствия.
3. Предложить варианты.
4. Дождаться согласования пользователя.

Не изменять продуктовую логику самостоятельно.

## 6. Требования к достоверности

ИИ должен разделять информацию на категории:

- подтверждённые факты;
- согласованные решения;
- предварительные решения;
- гипотезы;
- открытые вопросы;
- исторические сведения.

Нельзя выдавать предположения за подтверждённые факты.

Если данных недостаточно, нужно задать конкретный вопрос.

## 7. Правила выполнения задач

При работе над задачей:

1. Сначала определить относящиеся к ней документы.
2. Проверить, достаточно ли существующих данных.
3. Объяснить план ближайшего действия.
4. Не выполнять необратимые изменения без согласования.
5. Сохранять совместимость с текущей архитектурой.
6. Проверять результат подходящими средствами.
7. Фиксировать изменения в документации.

Для работы с пользователем предпочтителен последовательный режим: одно конкретное действие за раз, с подтверждением результата перед переходом к следующему действию.

## 8. Правила обновления документации

После существенного изменения необходимо определить, какие документы требуется обновить.

В зависимости от задачи это могут быть:

- `AI_CONTEXT.md`;
- `PROJECT_STATUS.md`;
- документы архитектуры;
- документы аудитов;
- документы принятых решений;
- история изменений.

Не ограничиваться обновлением только главной страницы.

Новые результаты аудита должны включать:
- дату проверки;
- область проверки;
- использованные источники и методы;
- установленные факты;
- выявленные проблемы;
- ограничения проверки;
- рекомендации;
- статус проверки.

## 10. Безопасность

Нельзя публиковать в открытой документации:

- API-ключи;
- пароли;
- токены доступа;
- секреты интеграций;
- персональные данные;
- приватные ссылки с полномочиями доступа;
- конфиденциальную информацию пользователей.

При обнаружении таких данных предупредить пользователя.

## 11. Завершение задачи

После выполнения задачи ИИ должен сообщить:

1. Что было сделано.
2. Какие документы изменены.
3. Какие проверки выполнены.
4. Какие проблемы остались.
5. Что является следующим актуальным шагом.

## 12. Главное правило

Новая ИИ-платформа подключается к уже существующему проекту EventFlow.

Она обязана использовать накопленные знания, уважать согласованные решения, сохранять историю и продолжать работу с актуального состояния.

Повторное изучение всей предметной области и проведение уже завершённых аудитов без причины не допускаются.
