
# EventFlow — Database Documentation

> Описание базы данных и правил работы с SQL-материалами.
> Последнее обновление: 11 ноября 2026 года.

## 1. Назначение раздела

Этот раздел описывает организацию документации базы данных EventFlow, расположение исторических SQL-файлов и правила безопасной работы с ними.

Основная backend-платформа проекта — Supabase с PostgreSQL.

## 2. Источники информации

Полная документация находится в приватном репозитории:

`eventflow-project-docs`

## 4. Критически важное предупреждение

**Исторические SQL-файлы нельзя автоматически запускать поверх действующей базы данных.**

Причины:

- фактическая схема могла измениться;
- некоторые объекты могли быть удалены или переименованы;
- первоначальный SQL может содержать уже устранённые дублирования;
- демонстрационные данные могут создать повторные записи;
- функции и политики могли измениться после первоначального аудита.

В частности, первоначальный файл схемы содержит дублирующий индекс `idx_rsvp_guest`, который позднее был удалён из рабочей базы.

Файл `02_seed_data.sql` содержит демонстрационные записи. Повторный запуск может привести к дублированию данных.

## 5. Правила работы с действующей базой

Перед любыми изменениями:

1. Получить фактическую текущую схему Supabase.
2. Изучить связанные таблицы, функции и политики.
3. Сравнить фактическое состояние с документацией.
4. Определить влияние изменения на существующие данные.
5. Подготовить отдельный SQL-скрипт или миграцию.
6. Проверить изменение в подходящей среде.
7. Зафиксировать результат в приватной документации.

Не выполнять разрушительные операции без явного согласования и проверки последствий.

## 6. Основные направления контроля

### Структура данных

- таблицы;
- столбцы;
- типы данных;
- первичные и внешние ключи;
- ограничения;
- индексы.

### Безопасность

- RLS;
- права доступа;
- GRANT и REVOKE;
- SECURITY DEFINER;
- search_path функций;
- права выполнения RPC.

### Бизнес-логика

- получение приглашений;
- обработка RSVP;
- проверка сроков;
- контроль принадлежности гостей;
- коммерческие права использования;
- организационная изоляция.

## 7. RSVP-функции

В исторической документации сохранены две ключевые функции.

### get_invitation(p_token text)

Возвращает данные приглашения по токену доступа.

### submit_rsvp(p_token text, p_responses jsonb, p_comment text DEFAULT NULL)

Обрабатывает ответы гостей.

В историческом определении `submit_rsvp` предусмотрены:
- проверка формата входных данных;
- проверка группы и мероприятия;
- блокировка соответствующих записей;
- проверка срока приёма ответов;
- проверка принадлежности гостя к группе;
- создание или обновление RSVP.

Эти сведения описывают сохранённую версию функции. Перед использованием необходимо сверить её с текущей реализацией.

## 8. Демонстрационные данные

В архиве имеется набор демонстрационных данных для мероприятия.

Он предназначен для исторического тестирования и не должен восприниматься как актуальные данные рабочей среды.

Перед повторным использованием необходимо проверить:
- уникальность записей;
- наличие соответствующих таблиц;
- внешние ключи;
- возможные конфликты;
- влияние на существующие данные.

## 9. Автоматические проверки

GitHub Actions выполняет SQLFluff Parse с диалектом PostgreSQL для первоначального SQL-архива.

Успешный разбор подтверждает возможность синтаксического разбора на уровне инструмента, но не доказывает:
- успешное выполнение в Supabase;
- корректность бизнес-логики;
- безопасность функций;
- актуальность структуры;
- отсутствие ошибок при выполнении.

## 10. Правила обновления документации

При изменении базы данных необходимо:

1. Обновить архитектурную документацию.
2. Зафиксировать новую миграцию или SQL-изменение.
3. Обновить описание затронутых сущностей.
4. Зафиксировать проверки.
5. Обновить соответствующий аудит, если он затронут.
6. Обновить PROJECT_STATUS.md при существенном изменении.

Исторические файлы следует сохранять как архив, не переписывая их задним числом.
