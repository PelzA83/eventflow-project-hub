
# EventFlow — Audit Registry

> Реестр аудитов и технических проверок проекта.
> Последнее обновление: 11 ноября 2026 года.

## 1. Назначение

Этот раздел содержит информацию о ранее проведённых аудитах EventFlow.

Его задача:
- сохранять историю проверок;
- предотвращать необоснованное повторение уже выполненной работы;
- помогать определять, какие области проекта требуют повторной проверки;
- связывать результаты аудитов с последующими изменениями.

## 2. Важное замечание об актуальности

Документы аудитов перенесены из предыдущих этапов работы над проектом.

Их наличие не означает, что:
- аудит выполнен 11 ноября 2026 года;
- текущее состояние приложения соответствует результатам аудита;
- схема Supabase не изменилась;
- все найденные ранее проблемы остаются актуальными;
- все ранее выявленные проблемы устранены.

Перед использованием результатов необходимо проверить дату, область и условия проведения конкретного аудита.

## 4. Как использовать предыдущие аудиты

Перед началом нового аудита:

1. Найти соответствующий исторический документ.
2. Изучить область проверки и выводы.
3. Определить, какие изменения произошли после проверки.
4. Проверить актуальность среды и исходных данных.
5. Повторять только те проверки, необходимость которых обоснована.

Не следует повторять полный аудит только потому, что задача перешла к другой ИИ-платформе.

## 5. Основные направления проверок

### 5.1. База данных

Проверяются:
- таблицы и связи;
- типы данных;
- ограничения;
- индексы;
- функции;
- соответствие структуры текущим требованиям.

### 5.2. Безопасность и RLS

Проверяются:
- политики доступа;
- изоляция организаций;
- права пользователей;
- права выполнения функций;
- доступ к данным через API;
- потенциальные способы обхода ограничений.

### 5.3. RSVP

Проверяются:
- получение приглашения;
- обработка ответов;
- проверка токена;
- принадлежность гостя к группе;
- сроки приёма ответов;
- повторная отправка и обновление ответа;
- корректность серверной обработки.

### 5.4. Приложение

Проверяются:
- пользовательские сценарии;
- интерфейс;
- взаимодействие с Supabase;
- обработка ошибок;
- авторизация;
- соответствие приложения продуктовым требованиям.

## 6. Автоматические проверки документации

В приватном репозитории настроен GitHub Actions workflow `EventFlow Documentation Check`.

В запуске #11 от 11 ноября 2026 года проверки завершились успешно.

Проверяются:
- наличие обязательных файлов;
- форматирование Markdown;
- синтаксический разбор SQL через SQLFluff Parse.

Эти проверки относятся к документации и архивным SQL-файлам. Они не заменяют функциональные, интеграционные и security-тесты приложения.

## 7. Правила фиксации новых аудитов

После проведения нового аудита необходимо:

1. Зафиксировать дату.
2. Указать проверенную среду и версию.
3. Перечислить область проверки.
4. Разделить подтверждённые проблемы и предположения.
5. Указать результаты и ограничения.
6. Зафиксировать рекомендации.
7. Сохранить полный отчёт в приватной документации.
8. Подготовить публичное резюме без конфиденциальных данных.
9. Обновить этот реестр и PROJECT_STATUS.md.

## 8. Принцип работы с проблемами

Каждая выявленная проблема должна иметь понятный статус:

- обнаружена;
- подтверждена;
- исправлена;
- проверена после исправления;
- неактуальна;
- требует дополнительного исследования.

Нельзя считать проблему исправленной только на основании изменения кода или SQL. Необходимо подтверждение соответствующей проверкой.
