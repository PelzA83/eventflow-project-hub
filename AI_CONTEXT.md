# EventFlow — AI Project Context

> Актуально на 14 ноября 2026 года. Этот документ — краткий входной контекст, а не полная спецификация или технический статус.

## 1. Цель проекта

EventFlow — платформа цифровых приглашений и решений для мероприятий.

Главная задача текущего этапа — как можно быстрее подготовить и начать демонстрировать два продукта:
1. Новогоднее приглашение — первое и более компактное.
2. Свадебное приглашение — следующее, на общей функциональной основе, с персонализацией, семейными приглашениями, независимыми RSVP и QR.

## 2. Текущий график

1. Документация и навигация приведены в порядок 14 ноября.
2. Целевой code review каркаса завершён: P0-блокеров по исходному коду не обнаружено; выявлены точечные P1-несоответствия.
3. Следующий этап — дизайн шаблонов на существующей функциональной основе.
4. По одному фиксированному шаблону для каждого продукта; интерфейс выбора альтернативных визуальных тем отложен. Стартовая страница временно показывает «Новогоднее» первым, подпись молодожёнов включена, смешанное семейное приветствие исправлено.
5. Подготовить и показать новогодний продукт первым.
6. Подготовить и показать свадебный продукт следующим.
7. Незначительные улучшения перенести на период после начала демонстраций.

Ранее обсуждавшиеся визуальные решения свадебного направления сохраняются как исходная база. Новогоднее визуальное направление предстоит разработать отдельно.

## 4. Принципы работы

- График выпуска важнее полноты платформы.
- Повторно использовать существующий код и общие функции.
- Не переписывать работающие части без подтверждённой причины.
- Не создавать универсальный редактор и функции «на будущее», если они не нужны для ближайшего показа.
- Не повторять аудит без конкретной необходимости.
- Не считать код доказательством готовности: пользовательский сценарий должен быть проверен.
- Разделять обязательные блокеры и отложенные улучшения.
- Архитектурные и продуктовые противоречия выносить на согласование.
- Не менять БД, архитектуру и приватный рабочий код без соответствующего разрешения.

## 6. Приоритет функций перед показом

- **P0:** основной путь организатор → персональная ссылка → приглашение → RSVP → результат у организатора; корректность данных и мобильного отображения.
- **P1:** обязательные особенности конкретного продукта. Для свадьбы — персонализация, семейные приглашения, независимые ответы и демонстрационный QR.
- **P2:** улучшения, которые не мешают эффектной демонстрации; их можно отложить.
- **P3:** production-инфраструктура, постоянное хранение и последующее развитие.

Подробные критерии см. в плане выпуска.

## 7. Достоверность

Различать согласованные требования, реализованный код, проверенные сценарии, ограничения, предложения и открытые вопросы. Исторические SQL и аудиты не считать описанием текущей системы без сверки. Не публиковать секреты и персональные данные.
