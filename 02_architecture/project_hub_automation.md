# Project Hub — архитектура автоматизации публикации

**Статус:** проектирование  
**Дата:** 11 ноября 2026 года  
**Назначение:** техническое задание на безопасную синхронизацию приватной документации EventFlow с публичным Project Hub.

## 1. Цель

Автоматизировать обновление публичного Project Hub на основании документации из приватного репозитория.

Целевая схема:

`Приватный репозиторий → проверка изменений → подготовка публичных материалов → одобрение → публикация → GitHub Pages`

Основная цель — исключить необходимость вручную переносить документы и поддерживать две копии информации.

Публичный Hub должен содержать только специально разрешённые обзорные материалы. Он не является зеркалом приватного репозитория.

## 3. Разрешённые материалы

Автоматизация использует предварительно утверждённый список файлов (allowlist).

| Публичный материал | Источник или способ формирования | Условие |
|---|---|---|
| `01_product/README.md` | Приватный `01_product/README.md` | Проверка перед публикацией |
| `02_architecture/README.md` | Приватный `02_architecture/README.md` | Проверка перед публикацией |
| `AI_CONTEXT.md` | `PROJECT_CONTEXT.md` и согласованные разделы | Подготовка публичной версии |
| `AI_HANDOFF.md` | Отдельный публичный документ | Обновление по правилам проекта |
| `PROJECT_STATUS.md` | Подтверждённые изменения и согласованные статусы | Не формировать предположения как факты |
| `llms.txt` | Структура опубликованного Hub | Автоматическая генерация |
| `index.html` | Структура опубликованного Hub | Автоматическое обновление навигации |

Новые типы документов и новые источники нельзя добавлять в allowlist без отдельного согласования.

Полные аудиты, SQL-файлы, архив базы данных, внутренние заметки и история рабочих обсуждений не публикуются автоматически.

## 4. Правила формирования публичных материалов

Автоматизация не должна механически копировать приватные документы, если они требуют адаптации.

Для каждого материала определяется отдельный способ обработки:

- прямая публикация разрешённого документа после проверок;
- подготовка публичной версии на основе нескольких источников;
- генерация навигации из фактически опубликованных файлов;
- обновление статуса только на основании подтверждённых изменений.

Содержимое приватных документов не должно автоматически становиться публичным только потому, что оно упоминает EventFlow.

## 5. Запуск автоматизации

Предусматриваются два способа запуска.

**Автоматический запуск:**
- после изменений в основной ветке `main` приватного репозитория;
- обрабатываются только изменения, относящиеся к разрешённым источникам.

**Ручной запуск:**
- через GitHub Actions (`workflow_dispatch`);
- используется для принудительной подготовки обновления Hub.

Повторный запуск не должен создавать дублирующие изменения и Pull Request.

## 6. Проверки перед публикацией

Проверки делятся на три уровня.

### 6.1. Проверка безопасности

Необходимо выявлять:
- API-ключи и токены;
- пароли и другие учётные данные;
- приватные адреса и конфиденциальные сведения;
- случайно добавленные внутренние материалы.

Используются автоматические сканеры секретов и дополнительные правила проверки.

Автоматический сканер не гарантирует обнаружение всех конфиденциальных сведений. Поэтому проверка содержимого и одобрение публикации остаются обязательными.

### 6.2. Проверка содержимого

Необходимо проверять:
- соответствие allowlist;
- отсутствие неразрешённых материалов;
- отсутствие неподтверждённых утверждений о реализации функций;
- согласованность публичных документов;
- корректность статусов и ссылок на приватные источники.

### 6.3. Проверка структуры

Необходимо проверять:
- корректность Markdown;
- существование файлов и ссылок;
- корректность навигации;
- соответствие структуры Hub фактическому содержимому;
- отсутствие ошибок генерации.

При провале любой обязательной проверки публикация блокируется. Причина ошибки сохраняется в логах GitHub Actions.

## 7. Порядок подготовки и публикации

Предполагаемый процесс:

1. GitHub Actions получает событие об изменениях или ручной запуск.
2. Определяет изменённые разрешённые источники.
3. Получает только необходимые данные приватного репозитория.
4. Формирует публичные версии документов.
5. Обновляет `PROJECT_STATUS.md`, `llms.txt` и `index.html` по согласованным правилам.
6. Выполняет проверки безопасности, содержимого и структуры.
7. При успешных проверках подготавливает изменения для публикации.
8. После необходимого одобрения создаёт Pull Request в публичном репозитории.
9. После одобрения и слияния Pull Request изменения публикуются через GitHub Pages.
10. Сохраняет результат выполнения и сообщает о нём.

### Важное ограничение публичного Pull Request

Публичный репозиторий открыт для всех. Поэтому содержимое новой ветки или Pull Request в нём может быть доступно посторонним ещё до слияния с `main`.

Следовательно, одного одобрения публичного Pull Request недостаточно для защиты от преждевременного раскрытия данных.

**Обязательное техническое требование:** до появления файлов в публичном репозитории должны быть завершены проверки и получено предварительное разрешение на публикацию.

Конкретный механизм двухэтапного одобрения необходимо определить при реализации. Рассмотреть GitHub Environments с ручным подтверждением до передачи материалов в публичный репозиторий.

## 8. Права доступа

Для межрепозиторного взаимодействия предполагается использовать GitHub App с минимально необходимыми разрешениями.

**Приватный репозиторий:**
- чтение разрешённых документов;
- отсутствие прав на изменение и удаление файлов.

**Публичный репозиторий:**
- подготовка отдельной ветки;
- создание Pull Request;
- отсутствие самостоятельного изменения основной ветки `main`.

Основная ветка изменяется только после предусмотренного одобрения.

Секреты GitHub App хранятся в защищённых GitHub Secrets. Права и срок действия учётных данных должны быть минимально необходимыми.

## 9. Автоматическое обновление Hub

Автоматизируются три элемента.

**`PROJECT_STATUS.md`**

Обновляется по подтверждённым изменениям, согласованным решениям и результатам проверок. Нельзя определять готовность функции только по наличию файла или упоминанию в документации.

**`llms.txt`**

Формируется на основании фактически опубликованных документов и их структуры.

**`index.html`**

Навигация обновляется на основании опубликованных разделов. Необходимо сохранять существующий дизайн и корректность ссылок.

## 10. Уведомления

Необходимо обеспечить уведомления о следующих событиях:

1. Обнаружены изменения и подготовлено обновление.
2. Проверки успешно пройдены.
3. Проверки обнаружили ошибку — публикация заблокирована.
4. Подготовлено одобрение публикации.
5. Изменения опубликованы.

На первом этапе достаточно уведомлений средствами GitHub: статусы Actions, логи выполнения и Pull Request.

Подключение Telegram, MAX или других каналов уведомлений не является обязательным.

## 11. Идемпотентность и защита от ошибок

Автоматизация должна:
- не создавать дублирующие Pull Request;
- не перезаписывать несвязанные изменения публичного репозитория;
- не удалять существующие публичные документы без отдельного согласования;
- не публиковать файлы вне allowlist;
- сохранять причину блокировки;
- корректно обрабатывать повторный запуск;
- не считать неудачное выполнение успешной публикацией.

При конфликте изменений автоматизация должна остановиться и сообщить о необходимости проверки.

## 12. Критерии готовности

Автоматизация считается реализованной, когда подтверждено следующее:

- [ ] Изменение разрешённого документа в приватном репозитории обнаруживается автоматически.
- [ ] Неизменённые и неразрешённые файлы не попадают в публикацию.
- [ ] Публичные версии формируются корректно.
- [ ] Секреты и конфиденциальные данные блокируют публикацию.
- [ ] Ошибки содержимого и структуры блокируют публикацию.
- [ ] До передачи материалов в публичный репозиторий получено необходимое одобрение.
- [ ] Pull Request создаётся без ручного переноса файлов.
- [ ] Основная ветка изменяется только после одобрения.
- [ ] `PROJECT_STATUS.md`, `llms.txt` и `index.html` обновляются по установленным правилам.
- [ ] Ручной запуск работает.
- [ ] Повторный запуск не создаёт дубликатов.
- [ ] GitHub Pages корректно публикует обновлённый Hub.
- [ ] Результаты и ошибки доступны в GitHub Actions.
