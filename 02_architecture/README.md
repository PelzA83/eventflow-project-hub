
# EventFlow — Architecture Overview

> Обзор архитектуры проекта.
> Последнее обновление: 11 ноября 2026 года.

## 1. Общая архитектурная концепция

EventFlow проектируется как модульный сервис с разделением:

- пользовательского интерфейса;
- серверной логики;
- хранения данных;
- авторизации;
- управления доступом;
- коммерческих прав использования;
- дополнительных функциональных модулей.

Архитектура должна обеспечивать изоляцию данных организаций, безопасность операций и возможность дальнейшего расширения продукта.

## 2. Основные компоненты

### 2.1. Клиентское приложение

Отвечает за взаимодействие пользователей с сервисом:

- регистрация и авторизация;
- управление организациями;
- создание мероприятий;
- управление гостями;
- настройка приглашений;
- просмотр RSVP;
- управление модулями и медиагалереей.

Фактический состав реализованных экранов необходимо проверять по текущей версии приложения.

### 2.2. Supabase

Supabase рассматривается как основная backend-платформа.

В архитектуре используются или предусматриваются:

- PostgreSQL — хранение данных;
- Supabase Auth — управление авторизацией;
- Row Level Security (RLS) — контроль доступа к строкам таблиц;
- SQL-функции и RPC — выполнение серверных операций;
- Storage — хранение файлов, если это предусмотрено соответствующим функционалом.

Наличие компонента в архитектуре не подтверждает его текущую настройку или готовность.

### 2.3. Авторизация

Согласованная модель:

1. Пользователь вводит номер телефона.
2. Система инициирует подтверждение через SMS OTP.
3. Supabase Auth проверяет код.
4. После успешной проверки создаётся или восстанавливается сессия.
5. Доступ к данным определяется членством в организациях и политиками безопасности.

Демонстрационный режим должен быть изолирован от реальной авторизации.

## 3. Основная модель данных

Ключевые сущности:

| Сущность | Назначение |
|---|---|
| organizations | Организации пользователей |
| organization_members | Членство пользователей в организациях |
| events | Мероприятия |
| groups | Группы гостей |
| guests | Гости |
| RSVP | Ответы на приглашения |
| modules | Дополнительные функции |
| entitlements | Права использования продукта |

Названия приведены как ориентир архитектурной модели. Фактические названия таблиц, полей и связей следует сверять с актуальной схемой Supabase.

## 4. Организационная модель

Связи верхнего уровня:

- пользователь может состоять в нескольких организациях;
- организация может иметь нескольких владельцев;
- мероприятие принадлежит одной организации;
- гости и группы относятся к конкретному мероприятию;
- доступ к данным ограничивается принадлежностью к организации и соответствующими правилами доступа.

Владельцы разных организаций не должны получать доступ к данным друг друга.

## 5. Модель доступа и безопасности

Основной принцип — проверка полномочий на серверной стороне.

RLS должен ограничивать доступ к данным с учётом:
- пользователя;
- организации;
- членства;
- роли;
- статуса сущности;
- допустимых операций.

Критические операции должны выполняться через контролируемую серверную логику.

Нельзя полагаться только на скрытие элементов интерфейса для защиты данных.

## 6. RSVP и серверные функции

В исторической документации зафиксированы две функции:

### get_invitation(p_token text)

Предназначена для получения информации о приглашении по токену доступа.

### submit_rsvp(p_token text, p_responses jsonb, p_comment text DEFAULT NULL)

Предназначена для обработки ответов гостей.

В архиве сохранены определения функций и диагностические SQL-материалы.

Важно: архив отражает историческое состояние. Перед изменением или повторным использованием функций необходимо сравнить их с текущей базой данных и проверить права выполнения, RLS и бизнес-логику.

## 7. Коммерческая архитектура

Права использования (entitlements) отделены от создания черновиков.

Основные принципы:
- право использования связано с организацией;
- создание черновика не расходует право;
- первое опубликование или активация расходует право;
- правила переноса и восстановления зависят от статуса мероприятия;
- возврат оплаты должен корректно отражаться в состоянии права использования.

Точная реализация требует проверки актуальной схемы и серверной логики.

## 8. Модульная архитектура

Дополнительная функциональность должна подключаться без необходимости создавать отдельную версию продукта для каждого клиента.

Предусмотрены:
- базовые функции;
- платные дополнительные модули;
- индивидуальные решения.

Модульность должна учитывать права доступа, коммерческие условия и принадлежность к мероприятию.

## 9. Медиагалерея

Архитектура медиагалереи должна предусматривать:

- привязку материалов к мероприятию;
- загрузку файлов;
- контроль доступа;
- модерацию;
- публикацию;
- разграничение ролей организатора, гостя и профессионального участника.

Материалы клиентов не становятся собственностью EventFlow автоматически.

## 10. Исторический SQL-архив

В приватном репозитории сохранены первоначальные SQL-файлы:

`04_database/initial/`

Архив включает:
- первоначальную схему;
- демонстрационные данные;
- определения RSVP-функций;
- проверки разрешений;
- проверки RLS;
- проверки индексов;
- проверки ограничений;
- проверки функций;
- тесты RSVP.

**Предупреждение:** архив не является миграцией для повторного запуска поверх действующей базы.

Перед любыми изменениями необходимо:
1. Получить актуальную схему Supabase.
2. Сравнить её с архивом.
3. Проверить зависимости.
4. Подготовить отдельное изменение.
5. Выполнить необходимые тесты.

## 11. Проверки и ограничения

GitHub Actions проверяет документацию и синтаксический разбор SQL через SQLFluff Parse.

Эти проверки не подтверждают:
- корректность выполнения SQL в Supabase;
- актуальность схемы;
- безопасность RLS;
- корректность бизнес-логики;
- работоспособность интерфейса;
- успешность пользовательских сценариев.

Для этого необходимы отдельные проверки в соответствующей среде.
